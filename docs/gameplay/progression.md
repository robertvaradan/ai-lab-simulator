# Progression

## Progression structure

Progression must give the player access to all Strategic Domains.

The game must not ask the player to select one permanent Strategic Domain.

The player must be able to invest in Research, Scale, and Applications in one campaign.

Limited Cash, staff, Compute Capacity, time, and trust must create trade-offs.

Unlocks must follow explicit requirements.

Elapsed time must not be the only unlock requirement.

## Cross-domain value

Research must improve or unlock Model outcomes.

Scale must supply Compute Capacity for Research, training, and Applications.

Applications must turn Models into contracts, Revenue, or strategic access.

Each Strategic Domain must depend on at least one other Strategic Domain.

No Strategic Domain must provide a complete dominant strategy by itself.

## Emergent company identity

The game can calculate a company archetype from completed investments and current assets.

The calculated archetype must be descriptive.

The calculated archetype must not restrict future Commands.

## Site progression

The player must unlock or improve predetermined Site Plots.

A Site Upgrade must change simulation state.

A major Site Upgrade must have a visible world-state representation.

A visual upgrade must not exist as the only source of a simulation effect.

The Simulation Core must own the effect.

## Scale progression

The early Company must use Third-Party Compute.

The player must be able to buy or reserve more Third-Party Compute.

Third-Party Compute must provide a fast Scale option.

Third-Party Compute must create a high ongoing cost.

Third-Party Compute presentation must use the Data Center World.

Later Scale progression can unlock owned Data Centers.

Owned Data Center presentation must use the Data Center World.

Owned Data Centers must require more Cash than Third-Party Compute.

Owned Data Centers must require more completion time than Third-Party Compute.

Owned Data Centers can supplement Third-Party Compute.

Owned Data Centers must be available to all company archetypes when their requirements are met.

A Research Giant can use owned Data Centers as supplemental Compute Capacity.

An Application Powerhouse can use owned Data Centers as supplemental Compute Capacity.

Hyperscaler progression must support owned Data Centers as the primary Compute source.

Hyperscaler progression must support exclusive use of owned Data Centers.

The Hyperscaler archetype can emerge from repeated Scale investments.

The Hyperscaler archetype must not lock other Strategic Domains.

## Competitor progression

Each Competitor must have an authored sequence of Competitor Stages.

A scenario must define the trigger for each Competitor Stage.

A trigger can use a Month Step, a Quarter Boundary, a World State condition, or a player milestone.

A Competitor Stage must list its state effects.

A Competitor Stage must not call the complete player planning system.

A flagship Competitor Model release must resolve during the Advance Competitors phase of the Month Step that ends the applicable Quarter.

The preceding Quarterly Report must identify a known flagship release quarter.

The preceding Quarterly Report can show a Projected Evaluation Range for that release.

The Projected Evaluation Range must not reveal the exact release values.

The actual Competitor release values must remain deterministic for a fixed Scenario.

## Model obsolescence

A Model must not lose value only because its age increases.

A Competitor release can move the technical frontier.

A Competitor release can change customer expectations.

A Market event can change Market Demand.

These changes can reduce a player Model's technical competitiveness.

These changes can reduce a player Model's market relevance.

These changes can reduce a player Model's pricing power.

These changes can reduce customer demand for a player Application.

The Simulation Trace must identify the event that caused each reduction.

## Recovery

A poor decision can create a lasting setback.

A setback must not cause an immediate hidden loss.

The player can recover when the current state and available Commands permit recovery.

The game must not create an unearned rescue event.

The game can reach an unrecoverable state before formal bankruptcy.

The interface must make severe deterioration visible.
